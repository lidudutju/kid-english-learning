# The password is generated, and the KDF is deliberately weak

Login checks the password with PBKDF2-SHA256 at **1,000 iterations** — two orders of magnitude
below any current recommendation. This is not an oversight. The Workers Free plan allows 10 ms
of CPU per request, and a properly stretched PBKDF2 (210,000 iterations) costs well over 100 ms
of pure CPU, so a conventional KDF cannot run here at all.

Key stretching exists to protect *low-entropy, human-chosen* passwords from offline guessing.
So instead of stretching a weak secret, we use a strong one: the password is generated by
`scripts/gen-password.mjs` with ~100 bits of entropy and is never chosen by a human. Against a
100-bit secret, 1,000 iterations versus 210,000 is the difference between "longer than the age
of the universe" and "longer than the age of the universe" — the stretching buys nothing that
the entropy has not already bought.

## Consequences

- The password **must not** be replaced with something memorable. Doing so silently removes the
  only thing making this safe. `scripts/gen-password.mjs` is the supported way to set it, and it
  is meant to live in a password manager, not in someone's head.
- Online guessing is bounded separately, by rate limiting on the login route — entropy does
  nothing about an attacker who only needs to be lucky once per request.
- The stored format carries its own iteration count (`pbkdf2$sha256$<iters>$<salt>$<hash>`), so
  moving to a paid plan means raising the number and re-running the script, not a migration.
- The same 10 ms ceiling constrains everything else on the request path: no per-request hashing
  of video bytes, no image work, and the nightly export must stay a straight serialise.
